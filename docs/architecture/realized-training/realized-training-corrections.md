# Realized training corrections

KAN-292 defines how manually recorded realized-training evidence can be corrected without erasing its history.

## Model

`workout_logs` remains the current/live projection consumed by H12 readiness and later tracking stories. A correction updates that projection, but the previous evidence is preserved in an append-only `workout_log_corrections` row.

Each correction stores:

- `workoutLogId` — stable identity of the corrected realized-training record;
- `correctedByUserId` — server-resolved actor;
- `correctedAt` — server-generated correction instant;
- `reason` — optional human explanation;
- `beforeSnapshot` — exact state immediately before the correction;
- `afterSnapshot` — exact state committed by the correction.

The snapshots include session/workout linkage, analysis date, actual occurrence instant, status, every realized metric with explicit `known` / `unknown` state, feeling and athlete notes.

## Invariants

1. **Correction is not replacement history.** The live row changes, but an immutable before/after audit fact is appended in the same transaction.
2. **`loggedAt` is immutable.** It remains the instant at which the realized record was originally captured. A correction has its own `correctedAt`.
3. **Unknown remains distinct from zero.** The correction updates both `workout_logs` storage values and `workout_log_evidence.knownMetricFields`; consumers must continue using the evidence sidecar to interpret numeric zero.
4. **Session linkage stays authoritative.** A replacement `sessionId` is revalidated through the same athlete/team/session boundary used on initial capture. No date/title/metric heuristic may establish linkage.
5. **Actor and athlete scope are server-owned.** Client requests cannot choose `athleteId` or `correctedByUserId`.
6. **Imported evidence is not silently rewritten as manual.** KAN-292 corrects manual evidence only. Future source integrations need source-aware correction/reconciliation rules.
7. **Soft-deleted records are not correction targets.** Correction lookup requires the current live realized record.
8. **Audit rows are append-only domain facts.** Product code must not edit or soft-delete correction rows as a normal correction workflow.

## Transaction boundary

A correction transaction performs three writes atomically:

1. update the live `workout_logs` projection;
2. update `workout_log_evidence.knownMetricFields` for metric knowledge state;
3. insert one `workout_log_corrections` audit row containing before/after snapshots.

If any write fails, none of the three changes may be observable.

## Read boundaries

- Athlete/team ownership is verified before correction history is exposed.
- Correction history is ordered oldest first so the sequence can be reconstructed deterministically.
- H12 readiness continues to read the current durable `RealizedTrainingRecord`; the audit trail explains how that current state was reached but does not create duplicate performed sessions.

## Persistence and rollout

SQLite and PostgreSQL/Supabase schemas both declare `workout_log_corrections`. The PostgreSQL migration must be generated by Drizzle, inspected, then applied and verified from an environment with Supabase direct credentials. Do not hand-edit generated Drizzle journal/snapshot metadata.

Until that environment verification exists, KAN-292 remains open even if repository, action and tests are otherwise complete.
