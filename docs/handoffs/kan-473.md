## KAN-504 entry contract

KAN-504 is the next story selected by Jira. It consolidates the existing Coach operational model:

```
Athlete
  → AthleteGroup
  → PlanningCohort
  → GroupTrainingPlan base / cohort variant
  → CompetitionEntry
```

The story must improve product framing, discoverability and entry points without creating parallel domain authorities.

Preserve:
- `assignAthleteToGroup` as the existing Athlete ↔ Group authority;
- AthleteGroup as stable sporting classification;
- PlanningCohort as a temporary subdivision of exactly one group;
- cohort variants derived from one base plan of the same group;
- H7/H9 dated membership, derivation, isolation and resolution invariants;
- CompetitionEntry ownership on the applicable plan/variant.

Do not absorb:
- cross-group PlanningCohort;
- athlete race-intent lifecycle from KAN-360;
- identity/auth/authorization from KAN-298;
- post-auth `data.ts` cleanup from KAN-472.

The fresh-story bootstrap must still inspect current code/tests and the complete KAN-504 Jira issue before proposing tasks.

## Cross-story decisions already frozen

### Weekly generation

The weekly pattern is an existing flexible preference, not a rigid calendar and not an ignored input. KAN-505 is about explaining real generator decisions, not replacing the engine or inventing provenance.

### Regionalization

KAN-506 must separate language, locale, calendar dates, timezone and currency presentation. Currency remains economic-domain authority and must never be inferred from locale. KAN-506 does not require new Team regional persistence unless current implementation proves it indispensable; any such schema decision must return to product review first.

### UI / responsive

KAN-507 owns the design-system/foundation decisions. Coach remains desktop-first; Athlete remains mobile-first. KAN-358 and KAN-359 must be reconciled rather than recreated.

### Cartographic minimum

KAN-507 begins with MapLibre using one simple monocolor track. The track must remain correctly georeferenced through:
- initial render;
- pan;
- zoom;
- `fitBounds`;
- resize;
- repeated combinations of those operations.

Before blaming MapLibre, isolate integration defects such as React lifecycle, container resize, source/layer recreation, style changes, coordinate ordering `[lon, lat]`, and `load/style.load` timing.

If MapLibre still cannot satisfy the minimum stably, compare the same monocolor track and the same criteria against the historical Leaflet implementation available in commit `61cf855de565ce53932b8153e9865a8919730747`.

Elevation-based track coloring is explicitly outside the minimum and does not block KAN-473. MapLibre is not removed by default; an alternative must prove parity before consumers are migrated and the old module is removed.
