## KAN-504 delivered baseline

KAN-504 consolidated the Coach model without introducing new domain authorities.

Visible vocabulary:
- ES: Grupo deportivo, Subgrupo de planificación, Plan base, Variante.
- EN: Sporting group, Planning subgroup, Base plan, Variant.

Operational model:
```text
Athlete
  → AthleteGroup / Sporting group
  → PlanningCohort / Planning subgroup
  → GroupTrainingPlan base / variant
  → CompetitionEntry
```

Delivered boundaries:
- `assignAthleteToGroup` remains the canonical Athlete ↔ Sporting-group mutation authority.
- A real group change on civil date `D` atomically closes open previous-group PlanningCohortMemberships on `D-1`; same-group assignment is a no-op; future changes/history rewrites are rejected.
- Sporting-group detail is now a natural Coach entry point for add/transfer, but reuses the same canonical mutation authority.
- Cohort variant derivation now has a real transactional persistence boundary around `derivePlanningCohortVariant`.
- Variant persistence copies strategies/preferences, hierarchy, microcycle targets and explicitly selected CompetitionEntries with remapped IDs; selected race-catalog sidecars are remapped too.
- Sessions and GroupSessionPrescriptions are not copied and variants remain `draft` until an explicit later Coach action.
- Planning-subgroup detail exposes derivation/review, validates eligible direct Base plans from the same group, reviews title/competitions and shows Base-plan lineage after creation.
- RaceCourse detail exposes a read-only planning-impact projection based only on persisted `competition_entry_race_courses` links. No name/date/distance inference is permitted.
- One RaceCourse may relate to independent variants in different Sporting groups; this never creates a cross-group Planning subgroup.

Durable contracts:

- `docs/architecture/competitions/race-catalog-planning.md`

## KAN-522 prescription-audience baseline

KAN-522 freezes the shared-planning-to-Session boundary as:

```text
compatible objective/horizon
        ↓
shared planning audience
        ↓
Base plan or Planning subgroup Variant
        ↓
Macro / Meso / Micro
        ↓
weekly generation
        ↓
shared Session
        ↓
prescription by planning scope
        ↓
Athlete dated planning resolution
```

Durable decisions:
- `Microcycle` is not conceptually the audience, but `microcycleId` is the
  canonical persisted identity from which the audience lineage is derived.
- `GroupSessionPrescription` uniqueness is `Session + microcycleId`, not
  `Session + groupId`.
- Base and Variant of the same Sporting group may coexist on one Session with
  distinct prescriptions.
- independent plan-first generations converge through `sharedEventKey`; no
  TeamWeeklyTemplate or new team-wide planning authority is introduced.
- regeneration is scoped to the active plan lineage, preserving sibling scopes,
  `manual`, and `generated_modified` records.
- shared Sessions are removed only after every active prescription has gone.
- Athlete resolves dated planning authority first. If Variant applies, it is
  complete authority for that date and there is no sparse per-Session Base
  fallback.
- Base is used only when no applicable Variant exists.
- `WorkoutLog` remains realized execution only.
- individual planned adjustments remain owned by KAN-521.

Durable architecture:
- `docs/architecture/planning/planning-cohorts.md`
- `docs/architecture/planning/session-generation.md`

KAN-505 must now explain this actual Base/Variant-aware generation and
prescription chain rather than the older group-only model.


## KAN-521 individual-adjustment baseline

KAN-521 adds one downstream individual planning layer without creating individual
Macro/Meso/Micro hierarchies and without using WorkoutLog as planning input.

Frozen behavior:
- logical identity is `athleteId + sourcePrescriptionId`;
- revisions are append-only with one current revision and durable reason audit;
- dose overrides cover only distance, duration, elevation gain and intensity;
- assignment overrides cover reschedule, stimulus replacement and omission;
- stimulus template IDs remain opaque in Coach UI; templates are selected by
  human label and validated server-side;
- stale source authority is shown as review-required and cannot be silently
  migrated to a new Base/Variant prescription;
- same-identity regeneration preserves the adjustment; new prescription identity
  makes the old adjustment stale;
- Athlete Plan and Home use the same KAN-522 + KAN-521 resolution path, so
  individual omission and other adjustments resolve consistently.

Walkthrough fixes captured during closure:
- Coach form remounts on revision change so persisted intensity is reflected
  immediately without browser refresh;
- current audit reason is visible in Coach review;
- all visible KAN-521 Coach copy is localized ES/EN;
- Home no longer uses the legacy group-only schedule loader.

Deferred i18n debt observed during the walkthrough remains owned by KAN-506:

- Home still contains inherited untranslated copy outside the KAN-521 surface.


## KAN-505 explainability baseline

KAN-505 explains the existing weekly generator without changing generator
authority, weekly-pattern semantics or regeneration ownership.

Durable behavior:
- `GenerationExplanation` is structured causal evidence for one generated
  planning-scope prescription, never one global explanation on a shared Session.
- causal stages are
  `weekly_budget → frequency → slots → stimulus_template → fixed_load → remaining_budget → flexible_allocation → intensity → coordination_reconciliation`;
- explanations are composed from the same real generator inputs/results and
  shared-event coordination used by the proposal;
- weekly pattern remains a flexible preference, and departures can explain
  omitted/alternate habitual days, recovery influence and race replacement;
- template compatibility, fixed geographic load, remaining/flexible allocation,
  intensity constraints and race separation are explainable without exposing
  internal numeric ranking scores;
- planning scope is Base or Variant and historical evidence stays scoped to the
  prescription/generation key;
- historical snapshots live only in
  `session_generation_modification_records.generation_explanation`;
- persisted provenance is structured and locale-neutral; presentation localizes
  codes to human ES/EN copy;
- Session detail reads persisted history rather than recomputing it;
- current ownership is shown separately from generated origin;
- `AthleteSessionAdjustment` stays Coach-owned/downstream;
- `WorkoutLog` stays realized-only and outside provenance.

## KAN-506 i18n and regional-consumption baseline

KAN-506 closes the MVP ES/EN localization debt in the audited Coach/Athlete
journeys and establishes an explicit regional-consumption boundary without
introducing persisted Team regional settings.

Frozen boundaries:
- `language`, presentation `locale`, operational `timeZone`, and economic
  `currency` are independent concepts;
- provisional application fallbacks are `es-AR`, `en-US`, and
  `America/Argentina/Buenos_Aires` until Initial Setup/KAN-298 supplies
  persisted authority;
- currency remains domain-owned and is never inferred from language, locale, or
  timezone;
- calendar dates, local planned date-times, and absolute instants remain
  semantically distinct; civil dates are not indiscriminately converted to UTC;
- timezone-dependent helpers receive timezone explicitly, with composition
  supplying the provisional fallback;
- localized navigation uses the existing `@/i18n/routing` boundary;
- stable domain codes remain language-neutral while presentation copy lives in
  ES/EN catalogs.

Walkthrough hardening removed legacy Spanish calendar tables and localized prose
from `lib/constants.ts`. HR-zone descriptive guidance now lives in
`DomainGlossary.heartRateZones`, RPE presentation in `Workouts.rpe`, and
athlete category/level presentation in `AthleteGroup` catalogs. Persisted
Coach-authored/session content is not treated as automatically translatable UI
copy.

KAN-506 introduced no regional schema/persistence. The Session-detail SQLite
failure found during walkthrough was local schema drift; applying the already
existing migrations and running `pn db:sqlite:verify` restored the supported
local schema without changing KAN-506 application code.
