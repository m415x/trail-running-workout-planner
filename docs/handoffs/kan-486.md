## KAN-461 acceptance audit

KAN-461's H3 intent is implemented without extending into H4.

- `Payment` is a historical fact associated with one persisted `MonthlyCharge`.
- Manual MVP registration supports only `cash` and `bank_transfer`.
- `paidAt` is preserved as the economic payment date and remains distinct from record creation time.
- Partial and full payments are supported.
- Corrections preserve logical `paymentId` and append a replacement revision.
- Explicit void appends a void revision; historical revisions are retained.
- Only each logical Payment's current non-void revision contributes to the effective paid amount.
- Effective payments cannot exceed H2-effective `amountDueMinor`.
- H2 reductions cannot lower an effective amount due below already-effective payments.
- No credit balance or automatic redistribution across periods exists.
- Mercado Pago is not modeled as a payment method; no provider/gateway/webhook/external-ID/checkout fields were introduced.
- H3 does not introduce aggregate `settled | pending | overdue` state, notices or Athlete blocking; those remain H4.

## Persistence and migration delivery

SQLite persists `payment_revisions` with positive amount and closed-method checks, a monthly-charge index and a partial unique current-revision index by logical Payment. Correction/void replacement is atomic.

During H3, the pre-existing generated migration lineage defect was exposed and repaired forward:

- SQLite H1/H2 journal history lacked intermediate generated snapshots before the H3 generation point. The normally generated H3 snapshot/journal were preserved and the SQL application delta was reduced to H3 only; generated metadata was not hand-edited.
- Supabase likewise had journal entries for H1/H2 without corresponding snapshots. The generated 0025 snapshot/journal were preserved and `0025_robust_thunderbolt_ross.sql` was reduced to the real H3 delta only.

The supported local SQLite lifecycle verifies `payment_revisions` at HEAD. An existing pre-H3 `sqlite.db` must be upgraded with `pn db:sqlite:upgrade`; the KAN-485 walkthrough exercised this recovery path after detecting a stale local schema.

PostgreSQL/Supabase H3 parity is versioned and remotely deployed in the verified environment. Final remote verification reported:

- H1 billing persistence contract: OK
- H2 billing persistence contract: OK
- H3 billing persistence contract: OK
- Application tables: 45/45
- Tables with RLS: 45/45

PostgreSQL truncated two long H2 FK identifiers. The verifier now checks those FKs structurally by source/referenced table and column instead of relying on names longer than PostgreSQL's identifier limit.
