# KAN-412 handoff

Status: **implementation verified on the story branch; integration into `dev` pending**.

Story branch: `kan-412-reference-percentage-contract`.

## Delivered behavior

- The canonical intensity method is `reference_percentage`; application values use `referencePercentage`, and persistence uses `reference_percentage`. A value of `90` means 90% of the applicable temporal 1000 m RunningReference; fractional representations such as `0.9` are not the 90% contract.
- Z1-Z5 remain an independent prescription system. There is no automatic conversion between HR zones and reference percentages, BPM, or 1000 m pace.
- The persisted workout type `PAM` remains unchanged; it is a workout-category identifier and must not be treated as a physiological PAM/MAS measurement.
- Session prescriptions use a closed coach-approved reference-percentage set: **50, 60, 70, 80, 90, 100, 110, 115, 120**. The form has no percentage preselected, uses a select rather than free numeric input, and server validation enforces the same set.
- ES/EN session copy distinguishes the intensity method from the percentage selector rather than repeating the same label. Trail/Hills execution remains effort-led and does not expose flat-reference pace/speed as an execution target.
- Legacy PAM-percentage mappings/helpers without current authority were removed after consumer migration. The canonical execution-guidance boundary remains authoritative.

## Persistence

- SQLite migration `0006_reference_percentage_contract` and Supabase migration `0022_reference_percentage_contract` rename the legacy percentage columns and values to the canonical contract. SQLite also includes the subsequent field-performance FK migration.
- SQLite is the development/runtime database. During the manual walkthrough the developer SQLite still had the legacy physical schema, so it was explicitly treated as disposable and rebuilt from the canonical schema plus seeds.
- Supabase is reserved for production and currently contains empty application tables. By explicit product-owner decision, KAN-412 does **not** apply migration 0022 to production during development.
- `pn db:verify:supabase` was intentionally run read-only and reported the deployed production schema still has the legacy columns. This is evidence that production has not received 0022; it is **not** a successful remote migration verification.
- Applying 0022 and then obtaining a GREEN remote verifier is a deployment responsibility. Do not claim the Supabase canonical contract is deployed until that occurs.
